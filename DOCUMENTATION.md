# How the documentation is generated

The published page (the style used by BiMERR, BOT, SAREF and most Linked Building
Data vocabularies) is produced by **WIDOCO**, which wraps LODE for the term
descriptions, OOPS! for pitfall scanning and Bubastis for changelogs.

Source: https://github.com/dgarijo/Widoco

## 1. Put the metadata inside the ontology

WIDOCO fills the sections of the HTML page from ontology annotations. Anything
missing is replaced by a red placeholder in the output. Add the relevant annotations either in Protege
(Active ontology tab, Annotations) or by editing the output file.

## 2. Export from Protege

`File > Save as...` and choose **Turtle** (recommended) or **RDF/XML**. Save to
`ontology/myont.ttl`. Check the ontology IRI is the namespace you intend to
publish, for example `https://w3id.org/myont`, and set an `owl:versionIRI` such
as `https://w3id.org/myont/1.0.0`.

## 3. Generate

Local build:

Once Docker is running, run this in cmd

```bash
./scripts/build-docs_windows.cmd
```

Equivalent manual command:

```bash
java -jar widoco.jar \
  -ontFile ontology/myont.ttl \
  -outFolder site \
  -getOntologyMetadata \
  -uniteSections \
  -includeAnnotationProperties \
  -lang en \
  -rewriteAll \
  -webVowl \
  -htaccess \
  -licensius \
  -oops
```

Useful flags:

| Flag | Effect |
|---|---|
| `-getOntologyMetadata` | reads title, authors, licence, version from the ontology annotations |
| `-uniteSections` | one single `index.html` instead of separate section files |
| `-includeAnnotationProperties` | documents annotation properties as well as classes and properties |
| `-webVowl` | adds the interactive WebVOWL diagram tab |
| `-oops` | embeds the OOPS! pitfall evaluation (needs network access) |
| `-htaccess` | writes an `.htaccess` for content negotiation |
| `-licensius` | resolves the licence name and icon from the licence URI |
| `-rewriteAll` | overwrites previous output without prompting |
| `-crossRef` | regenerates only the cross-reference section, keeping your hand-edited sections |
| `-confFile FILE` | uses a properties file instead of ontology annotations |

Running `java -jar widoco.jar` with no arguments opens the graphical wizard,
which is the easiest way to see which metadata is missing.

## 4. Edit the narrative sections

WIDOCO writes editable HTML fragments under `site/sections/`
(`introduction-en.html`, `overview-en.html`, `description-en.html`,
`crossref-en.html`, `references-en.html`). Add the diagrams and prose there,
then regenerate with `-crossRef` so your edits survive.

Put figures in `site/resources/` and reference them with relative paths.

## 5. Publish

The workflow in `.github/workflows/publish-docs.yml` regenerates the site on
every push that touches `ontology/` and deploys it to GitHub Pages. Enable it
once under `Settings > Pages > Build and deployment > Source: GitHub Actions`.

## 6. Quality checks before release

- OOPS! pitfall scanner: https://oops.linkeddata.es/
- FOOPS! FAIR assessment: https://foops.linkeddata.es/FAIR_validator.html
- W3C RDF validation of each serialisation
- A reasoner run in Protege (HermiT or ELK) with no inconsistencies

## 7. Persistent URI

GitHub Pages cannot do content negotiation, so the `.htaccess` generated by
WIDOCO does nothing there. Register the namespace at
[w3id.org](https://github.com/perma-id/w3id.org) instead and let it redirect to
the GitHub Pages URL. See `w3id/README.md`.
